# Design note: bundling Keycloak as the default identity provider (ADR 0106)

Status: **design note — not built.** This settles the open questions ADR 0106 left to this
note (packaging, database, the issuer-URL problem, starter-realm contents, how `booth-admin`
reaches it, security posture, external-provider compatibility, CI) before any chart/CRD/Go code
changes. Where a question genuinely needs a decision this note doesn't have standing to make
(Ingress/TLS), it says so explicitly rather than picking one silently.

Nothing here changes `oidc.*`'s existing meaning or default for an operator already running an
external provider — every recommendation below is additive, gated behind a new `keycloak.enabled`
value that defaults to `true` but costs nothing to flip off.

## a) Packaging: a small, repo-owned template on the official image — not a subchart, not the operator

**Recommendation: mirror `templates/postgresql.yaml`'s own precedent exactly** — a hand-written
`Deployment` + `Service` + `ConfigMap` (the starter realm) on the official
`quay.io/keycloak/keycloak` image, pinned by digest, not a third-party Helm chart and not the
Keycloak Operator.

This is the same call `docs/decisions/0008-shared-postgres.md` already made and explained for
PostgreSQL, and the reasoning transfers directly:

- **Not a subchart.** The obvious candidate (Bitnami's) ties the platform's default identity
  provider to one vendor's image-distribution policy — `0008` already rejected this exact pattern
  for PostgreSQL after Bitnami's free-tier terms shifted, and a self-hosted platform's login path
  is a worse thing to have break from an upstream licensing change than its database. A ~100-line
  template on the official image has no such dependency.
- **Not the Keycloak Operator.** The Operator adds a CRD, its own controller, and real
  operational surface (reconciliation loops, its own upgrade story) that buys nothing for a
  single-replica, non-HA, self-hosted default — the identical "don't adopt a heavier abstraction
  than the problem needs" judgment this repo already made for its own `BoothModule` controller
  versus a generic injector (ADR 0095's "no pod-mutating webhook... not before a second or third
  real need"). Worth reconsidering only if a real multi-replica/HA Keycloak need materializes,
  which a single-node homelab default never will.

**Starting point and what changes from it.** `booth-e2e/bringup/keycloak.yaml` is the right shape
to start from — a `Deployment` + `Service`, one container, a realm mounted from a `ConfigMap` —
but it is explicitly a *throwaway test fixture* ("nothing here needs to survive the droplet") and
several of its choices are wrong for a real bundled default:

| `booth-e2e`'s `keycloak.yaml` | This chart | Why |
|---|---|---|
| `args: ["start-dev", "--import-realm"]` | `start --import-realm` (production mode) | `start-dev` uses an in-memory/ephemeral embedded H2 database and disables several production safeguards (strict hostname checking among them) — acceptable for a droplet that's torn down after one test run, not for a real install whose realm/users must survive a restart. |
| No explicit database config (dev-mode embedded H2) | `--db=postgres` against core's shared PostgreSQL | See (b) below. |
| No `KC_HOSTNAME` (dev mode derives `iss` from the request's `Host` header) | `KC_HOSTNAME` set explicitly to one fixed, chart-templated value | See (c) below — this is the one load-bearing behavioral change, not just a hygiene one. |
| `image: quay.io/keycloak/keycloak:26.0` (floating tag) | the same image, pinned by digest (`quay.io/keycloak/keycloak@sha256:...`) | Matches this repo's own established convention (`ghcr.io/projectbooth/minio-test`, `credential-sidecar` — ADR 0087/0091) and this week's finding that a floating tag on a registry outside this project's control can go stale or get locked down with no warning (the `quay.io/minio/minio` anonymous-pull lockout found and fixed in `.github/workflows/integration.yml` this same week). The exact digest to pin is chosen at build time against whichever Keycloak release this note's reviewer settles on (26.x is the natural candidate, already proven reachable anonymously — confirmed directly against the registry while verifying `scripts/booth-admin`, not assumed). |
| Admin password: `KC_BOOTSTRAP_ADMIN_PASSWORD` from a Secret the *bringup script* creates ad hoc | The same env var, but the Secret is generated by **core itself** at startup | See (d)/security below — `booth-e2e`'s own Secret creation is fine for a script that owns the whole cluster's lifecycle; a real chart needs the same create-then-adopt mechanism `internal/dbprov.EnsureAdminPassword` already uses for the bundled PostgreSQL's own superuser password. |
| Realm: `realm-booth.json.tpl`, four sample users, a password template substituted in at bringup | No sample users, no sample workspaces, `registrationAllowed: false` | ADR 0106 item 2, explicit. See (d). |
| `readinessProbe` on `/realms/booth` | Same shape, against whichever realm name this note's reviewer picks | No change needed — this part of `keycloak.yaml` is already correct for a real install. |

Not templated as a Helm subchart dependency; folded into `booth-core`'s own `templates/`, gated
by `{{- if .Values.keycloak.enabled }}` the same way `postgresql.yaml` is gated by
`.Values.postgresql.enabled` — one release, one chart, matching how NATS and PostgreSQL are
already "batteries included, swappable."

## b) Database: core's shared PostgreSQL, not Keycloak's own volume

**Recommendation: Keycloak's database lives on the same bundled PostgreSQL every module's
database already lives on (ADR 0053/0054), provisioned the same way core provisions its own.**

The alternative — Keycloak's own PersistentVolumeClaim — was considered and rejected:

- Keycloak's embedded H2 (what `start-dev` uses, and what a persistent-H2 PVC would also mean)
  is explicitly **not a production database** per Keycloak's own documentation, even for a
  single-node deployment. Using it would contradict this platform's own stated production-
  readiness goal for the sake of avoiding a dependency this chart already has.
- A *second*, dedicated Postgres instance just for Keycloak would duplicate the entire
  `templates/postgresql.yaml` StatefulSet (and its backup CronJob) for one more piece of core
  infrastructure, directly against the "one shared Postgres, swappable" philosophy `0053`/`0054`
  already established — and `0053`'s own prose already draws this exact parallel ("PostgreSQL:
  batteries included, swappable, like NATS and Keycloak").

**Mechanism**: `internal/dbprov.Provisioner` already has exactly the generic primitive this
needs — `EnsureCore` provisions core's *own* database/role/Secret on first start, by calling the
same `ensure(ctx, key, name, owner)` every module's database goes through. The build phase adds
one more call of that same shape — `EnsureKeycloak(ctx, namespace)`, or simply a second call to
the existing `ensure` with `name = "booth_keycloak"` — run from core's own startup, gated on
`keycloak.enabled`, producing a Secret (`booth-keycloak-db`, naming TBD) holding a DSN for a
dedicated `booth_keycloak` database and role. The Keycloak `Deployment` waits on that Secret to
exist before its container can start — the identical "pod sits in `ContainerCreating` until core
has generated the credential" pattern `postgresql.yaml`'s own comment already documents for the
bundled server's *own* superuser password. No new primitive, no new bootstrapping mechanism —
one more call to code that already exists and is already exercised in CI.

**Ordering, stated plainly**: core's own process provisions Keycloak's database directly against
the shared Postgres server — this needs Postgres reachable, not Keycloak. Keycloak reaching
*readiness* needs its database Secret to exist, which needs core's process to have started and
run that provisioning step, which does not itself wait on Keycloak. There is no circular
dependency; the two subsystems are provisioned in a strict order (core's DB logic, then
Keycloak's own startup) but core's own `/healthz` and HTTP server do not block on Keycloak being
reachable either (`initVerifierWithRetry` already retries OIDC discovery in the background,
unchanged by any of this).

**Backup and upgrade consequences — both already solved, not new work**:

- **Backup**: `charts/booth-core/files/pg-backup.sh` already dumps *every* non-template database
  that accepts connections on the server, discovered live via a `pg_database` query — not a
  hardcoded list. Keycloak's database is automatically included in the existing backup CronJob
  the moment it exists on that server, with zero changes to the backup script itself.
- **Upgrade**: `docs/runbooks/postgres-backup-restore.md`'s existing major-version-upgrade
  runbook (dump → fresh server → restore) covers Keycloak's data the same way, for the same
  reason. Keycloak's own application-level schema migrations (run automatically by the Keycloak
  container itself against whatever Postgres major version it's pointed at) are an orthogonal,
  separate upgrade axis from Postgres's own major-version upgrades, and need their own line in
  that runbook once this is built — noted here so it isn't forgotten, not solved in this note.

One real new coupling, stated honestly: a Postgres outage or restart now also takes down the
identity provider, not just module data access. Accepted — the shared server was already a
single point of failure for every module's own database before this, and splitting Keycloak onto
its own infrastructure to avoid that coupling would cost a second bundled database for a
single-node, non-HA default that has no HA story for *either* piece today.

## c) The issuer-URL problem

**This is the one genuinely hard part, and the one place `booth-e2e`'s own approach is
explicitly a workaround, not a pattern to copy as-is.** `booth-e2e/bringup/DEVIATIONS.md`'s
"Issuer must match" finding: in dev mode, Keycloak stamps a token's `iss` from the *request's own
`Host` header* — so the exact string depends on how a particular request happened to reach it. The
e2e runbook's answer is to alias the in-cluster DNS name into `/etc/hosts` on the test droplet and
port-forward on a matching port, so the browser's request and a pod's request produce an
identical `Host` header by coincidence of configuration. That is workable for one operator on one
droplet who controls both ends; it is not a instruction a homelab operator should be handed.

**The real fix is not to rely on request-echoing at all.** Keycloak's "hostname v2" provider
(`KC_HOSTNAME` and related `KC_HOSTNAME_*` settings — exact flag surface to be confirmed against
the pinned image version at build time, not asserted here) lets an administrator set **one fixed,
explicit issuer string**, stamped into every token regardless of which network path a given
request actually took. This turns "the browser's request happens to match" into "reachability,"
which is a more honest problem to solve, and converts `oidc.issuerUrl` and Keycloak's own hostname
setting into **the same value, templated from one chart value, not two independently-set ones** —
removing the exact class of drift `booth-e2e` had to work around by hand.

**What's actually hard, stated plainly: that one fixed URL still has to be reachable by both the
user's browser and every pod**, and `ARCHITECTURE.md` item 37a is explicit that there is no
Ingress controller, TLS, or DNS/public-hostname story anywhere in this platform yet. Three real
options exist today, with real trade-offs — this note picks one as the v0 default and names the
other two as what an operator can already choose instead, rather than pretending there's only one
answer:

1. **NodePort + the node's own reachable address (the v0 default this note recommends).** A
   single `Service` of type `NodePort` exposes Keycloak's HTTP port on every cluster node; on a
   genuinely single-node homelab (the explicit target: k3s or similar), the node's own LAN IP (or
   `localhost`, if the operator's browser runs on the same machine as the cluster) reaches it
   directly, and — critically — so does every pod *inside* the cluster, since a NodePort is
   reachable from inside the cluster via the node's address too, not only from outside it. No
   Ingress needed. The chart takes one new required value when `keycloak.enabled=true` — call it
   `keycloak.hostname` (e.g. `192.168.1.50:30180`, no scheme, since there is no TLS yet) — and
   templates both `KC_HOSTNAME` and the default `oidc.issuerUrl` from that *same* value, so they
   cannot independently drift. **What breaks if the operator gets it wrong**: if
   `keycloak.hostname` is stale (the node's DHCP lease changed) or unreachable from the operator's
   own network, the browser's login redirect fails outright — a clear, loud failure, not a subtle
   one, since OIDC discovery itself 404s/times out. If an operator somehow sets `oidc.issuerUrl`
   independently of `keycloak.hostname` (bypassing the chart's own templating, e.g. via a direct
   `--set oidc.issuerUrl=...` override) and the two values disagree, *every* login fails with an
   issuer mismatch, not a partial degradation — core's own token verification treats this as an
   exact-string comparison, same as the gap `booth-e2e` found. The chart's templating removing the
   chance to set these independently is the actual mitigation, not documentation alone.
2. **`kubectl port-forward` (fine for one-off admin access, not a sustained login path).** Works
   today with zero chart changes, but a port-forward dies when its terminal closes — it's the
   right tool for `booth-admin`'s own first-run bootstrap (see (e) below) and for an operator who
   wants a one-off look at the admin console, never for the URL real end-users sign in through
   day to day.
3. **A real hostname behind an Ingress, with TLS.** The actually-correct long-term answer, and
   explicitly **not decided here** — `ARCHITECTURE.md` item 37a already names "no Ingress
   controller, TLS, or DNS/public-hostname story anywhere" as its own open, cross-cutting gap,
   and this note does not resolve it on Keycloak's behalf alone. **Proposed, not decided**: once
   an Ingress/TLS ADR exists, `keycloak.hostname` (and the matching `oidc.issuerUrl` it derives)
   becomes a real DNS name over `https://`, and option 1's NodePort becomes the fallback for an
   operator who hasn't set up Ingress yet rather than the only option. Flagging this explicitly,
   per instruction, rather than quietly building toward it as if it were already settled.

## d) The starter realm

Per ADR 0106 item 2, the starter realm (a `ConfigMap`, mounted at
`/opt/keycloak/data/import`, imported via `--import-realm` on first boot) contains:

- **The `workspaces` group tree convention (ADR 0025), with no sample workspaces.** Just the
  bare top-level `workspaces` group — `booth-admin create-workspace` creates every
  `/workspaces/<slug>/{owner,editor,viewer}` subtree from there, exactly as it already does
  against `booth-architecture/local-dev`'s realm.
- **The `platform`/`operator` group (ADR 0094), empty** — no user pre-granted it. The very first
  operator grant is also a `booth-admin grant-operator` call, post-install, by whoever is
  physically at the keyboard for the install (see (e)).
- **A public client for the shell**, `booth-design`-shaped: `publicClient: true`,
  `standardFlowEnabled: true`, PKCE required (`pkce.code.challenge.method: S256`, matching both
  `booth-e2e`'s and `local-dev`'s realms), `directAccessGrantsEnabled: false` (the shell never
  needs a non-interactive password grant; `booth-admin` talks to the *admin* API, not this
  client, and needs no client of its own — see (e)). **Redirect URIs and web origins are templated
  from `keycloak.hostname`/the shell's own reachable origin, not `booth-e2e`'s `"*"` wildcard.**
  A wildcard redirect URI is fine for a throwaway test fixture; it's a real open-redirect-shaped
  risk to ship as a *default* for every real install, and costs nothing to scope correctly since
  the chart already knows the shell's own reachable address.
- **The full-group-path `groups` mapper**, attached via a **dedicated `groups` client scope**
  (the `local-dev` / `scripts/testdata/ci-realm.json` pattern — `oidc-group-membership-mapper`,
  `full.path: true`, added to the realm's `defaultDefaultClientScopes`) rather than
  `booth-e2e`'s pattern of attaching the mapper directly on one client. The scope-based form is
  the one already proven in this repo's own CI (`booth-admin-check`), and scales to a second
  client (e.g. a future `booth-api` public client) picking it up automatically rather than needing
  the same mapper copy-pasted onto every client that needs it.
- **`registrationAllowed: false`.** Self-registration was never asked for and isn't part of this
  platform's account model — every account is created by `booth-admin`.
- **No sample users, no sample workspaces, no default passwords anywhere** — the one point ADR
  0106 item 2 is most explicit about, and the one place this note departs furthest from *both*
  `booth-e2e`'s `realm-booth.json.tpl` (four sample users, a templated-but-shared password) and
  `local-dev`'s own realm (four sample users, a hardcoded `booth-dev-password`). Those are correct
  for their own purposes (a disposable e2e smoke test; a local-dev convenience where "secure" was
  never the point) and wrong for anything that bundles into a real install. `booth-admin` is
  already the supported path for the first real workspace and user, per ADR 0106 item 2.
- **Brute-force protection on** (`bruteForceProtected: true`) — the realm default is `false`, and
  neither `booth-e2e`'s nor this repo's own just-shipped CI fixture (`scripts/testdata/ci-realm.json`)
  turns it on, correctly, since neither needed to defend a real account. A realm that ships as a
  real install's default should not inherit that same omission.

**Admin password**: generated at install by core itself, into a Secret — the exact mechanism (d),
not a chart default — see (f) for why this is the actual security boundary here, not network
isolation.

## e) How `booth-admin` finds and authenticates to this Keycloak

No new mechanism — `scripts/booth-admin` already refuses a plain `http://` `KEYCLOAK_URL` against
anything but `localhost`/`127.0.0.1` (deliberately, so the admin password and every token it
fetches never cross the network in the clear), which means the bundled Keycloak's own
`keycloak.hostname` (a bare LAN IP:port, per (c)) is **not** something `booth-admin` should be
pointed at directly — the same port-forward pattern `docs/operations/accounts-and-workspaces.md`
already documents for "a real cluster" is the answer here too, not a new one:

```sh
kubectl -n booth-system port-forward svc/<release>-keycloak 8081:8080
export KEYCLOAK_URL=http://localhost:8081
export KEYCLOAK_REALM=booth          # the chart's fixed starter-realm name
export KEYCLOAK_ADMIN_USER=admin     # the chart's fixed bootstrap admin username
export KEYCLOAK_ADMIN_PASSWORD=$(kubectl -n booth-system get secret booth-keycloak-admin -o jsonpath='{.data.password}' | base64 -d)
python3 scripts/booth-admin create-workspace home
```

This is exactly the "install, then run `booth-admin create-workspace`" flow ADR 0106 asks for,
using infrastructure (port-forward, a generated Secret) that already exists in this platform's
own conventions — nothing new to build for `booth-admin` itself.

## f) Security

- **Admin console exposure — the honest answer, not a mechanism this note invents.** Without an
  Ingress or any other path-aware reverse proxy in front of Keycloak (item 37a, again), a bare
  `NodePort` `Service` cannot split "the login/OIDC endpoints end users need" from "the admin
  console" by *path* — both live on the same container port, and Kubernetes `Service` routing has
  no concept of HTTP path. So for v0, **the admin console is necessarily reachable on the same
  exposed surface as login**, and the real security boundary is the generated admin password
  itself (never a chart default, delivered only via a Secret an operator must deliberately read —
  (d)/(e) above), not network isolation. Properly isolating the admin console to an
  operator-opt-in-only surface needs the same path-aware routing capability item (c)'s longer-term
  option already flags as undecided — this is a second, independent reason that gap matters, not
  a new one.
- **Token lifetimes**: left at Keycloak's own realm defaults rather than inventing new numbers.
  `docs/operations/accounts-and-workspaces.md` already documents that a membership change takes
  effect on the user's *next token refresh* — shortening access-token lifetime well below
  Keycloak's default would make that propagate faster at the cost of more refresh traffic;
  lengthening it works the other way. No evidence yet that either extreme is needed; revisit with
  a concrete complaint, not preemptively.
- **Brute-force protection**: on, in the starter realm (see (d)) — this realm ships as a real
  install's actual defense surface, unlike the throwaway/local-dev realms that came before it.
- **NetworkPolicy, if `networkPolicy.enabled`**: mirrors `networkpolicy-postgresql.yaml`'s shape,
  but **cannot be scoped as narrowly**. PostgreSQL's policy only needs to admit namespaces
  labelled as database clients; Keycloak's OIDC discovery/JWKS endpoints need to be reachable by
  *every* module's pod that independently re-verifies a token (ADR 0041 — that's the whole fleet,
  not an opt-in subset). The policy admits ingress from any namespace, same posture as not having
  one for this specific traffic class; worth stating plainly rather than writing a policy that
  looks restrictive but admits everything in practice.
- **Deliberately left for later, named rather than silently skipped**: Ingress/TLS (above, twice);
  a real secrets-management story beyond "generate into a Kubernetes `Secret`" (`ARCHITECTURE.md`
  item 37a's own `(c)`, already a fleet-wide open item, not re-decided here); SMTP configuration
  for email-based self-service password reset (meaning a locked-out user needs an operator to run
  `booth-admin` on their behalf — and `booth-admin` itself has no "reset a user's password"
  subcommand today, a real gap in that script worth its own small follow-up, not this note's to
  build); MFA/WebAuthn (not asked for).

## g) `keycloak.enabled=false` and the existing `oidc.*` values

**No change to what they mean or do.** `keycloak.enabled` is a new, independent value; when
`false`, every template this note adds is simply not rendered (the same `{{- if .Values.X.enabled }}`
gate `postgresql.yaml`/`nats` already use), and `oidc.issuerUrl`/`oidc.clientId` behave exactly as
they do today — required, operator-supplied, pointed at whatever external provider the operator
already runs.

**How that's tested**: it already is, today, by `kind-deploy`'s existing install step —
`--set oidc.issuerUrl=https://keycloak.example.com/realms/booth --set oidc.clientId=booth-core`
is *already* the external-provider path this job has exercised all along, since the chart has
never had a bundled Keycloak to default to until this note. The one real change needed in CI once
`keycloak.enabled` defaults to `true`: that existing install step must add
`--set keycloak.enabled=false` explicitly, so it keeps testing exactly what it has always tested
(the external-provider path, with a deliberately-unreachable fake issuer) rather than silently
also standing up a bundled Keycloak it was never meant to exercise. Naming this now so it isn't
missed during the build phase; the actual `--set` addition is a one-line change to
`.github/workflows/integration.yml`, not built here.

## h) Testing the bundled default in CI

A new check, in the same `kind-deploy` job (or a sibling job, decided during the build phase) —
**installing the chart with no `oidc.*`/`keycloak.enabled` overrides at all**, i.e. the true
bundled default, then:

1. Wait for the bundled Keycloak `Deployment` to roll out (the same `rollout status --timeout=`
   pattern every other `kind-deploy` check already uses).
2. Run `scripts/booth-admin create-workspace`/`create-user`/`add-member` **from inside the
   cluster** — a `Job` in the same shape as the existing `bus-check`/`db-check` Jobs this workflow
   already runs, not a port-forward out to the GitHub runner (consistent with how every other
   `kind-deploy` check that needs in-cluster connectivity already works, and sidesteps needing to
   solve (c)'s reachability question for a CI run that has no real "browser" at all) — pointed at
   Keycloak's own in-cluster Service DNS name directly (`http://<release>-keycloak.booth-system.svc:8080`),
   no `KEYCLOAK_URL` localhost restriction to route around since this Job *is* inside the cluster.
3. Obtain a real token for the created user the same way `scripts/testdata/ci-realm.json`'s own
   `booth-admin-check` job already does (reset to a non-temporary password via the admin API,
   fetch a token via the starter realm's public client, decode it) and assert the `groups` claim
   reads exactly `["/workspaces/<slug>/<role>"]` — proving the starter realm's own mapper (d)
   actually produces what ADR 0025's grammar needs, not just that `booth-admin`'s own CI fixture
   does.
4. From that same in-cluster `Job`, call `booth-core`'s own in-cluster Service
   (`http://<release>.booth-system.svc:8080/api/me`) with that token and `X-Workspace`, and assert
   the returned `active.workspace`/`active.role` match — the full chain, bundled Keycloak through
   core's own API, with nothing stubbed.

This is the identical sequence `booth-admin-check` already proves against its own disposable
fixture, run one more time against the *real* bundled chart's *real* starter realm — the thing
that would have caught a starter-realm mistake (a missing mapper, a wrong client setting) that a
fixture built independently of the real chart could never catch.

## Spike result, 2026-10-08: secure-context question (coordinator condition 1) — FAILS

Per the coordinator's instruction, this was tested empirically on a real `kind` cluster before
any chart work, using the pinned image from (a)
(`quay.io/keycloak/keycloak@sha256:09a381c715ab0b111835b70f2905955274843a219c6f27efb348e4d9f4086858`,
Keycloak 26.0.8) and the proposed `KC_HOSTNAME`/`KC_HTTP_ENABLED` hostname setup from (c).

**Setup:**
- Keycloak deployed as a real `Deployment` + `NodePort` `Service` on a dedicated `kind` cluster
  (`keycloak-spike`), reachable at the node's Docker-assigned IP on a NodePort
  (`http://<node-ip>:30180`) — a real non-localhost, plain-http origin, the same shape a homelab
  NodePort install would present.
- A starter-realm-shaped import (`workspaces`/`platform/operator` groups, a full-path `groups`
  client-scope mapper, a public client `booth-design` with `standardFlowEnabled`,
  `pkce.code.challenge.method: S256`, matching `redirectUris`/`webOrigins`) imported on first boot.
- A minimal stand-in "shell" page (static HTML+JS, no framework) implementing a real Authorization
  Code + PKCE flow by hand — `crypto.getRandomValues` for the verifier,
  `crypto.subtle.digest('SHA-256', ...)` for the challenge, base64url encoding, redirect to
  Keycloak's `/auth`, and a callback page exchanging the code for a token via `fetch` — served from
  a second `NodePort` on the same node IP (`http://<node-ip>:30181`), so the shell's own origin is
  also non-localhost plain http.
- A real Chromium (Playwright, no flags weakening secure-context behavior) navigating to the
  shell's non-localhost http origin and driving the login end-to-end.

**Result — browser leg: FAILS.** Chromium reports `crypto.subtle` as `undefined` on the shell's
origin before any redirect to Keycloak happens:

```
STATUS: checking crypto.subtle...
STATUS: LOGIN_FAILED: crypto.subtle is unavailable (insecure context) - cannot generate PKCE code_challenge
```

This is exactly the risk named in condition 1: the Web Crypto `SubtleCrypto` interface is only
exposed by the browser on a secure context (`https:`, or `http:` on `localhost`/`127.0.0.1`/
`[::1]`), and a NodePort on a LAN/Docker-assigned IP over plain `http` is none of those. The
failure is unconditional and happens on the shell's own page, before Keycloak is even reached —
it is not something the realm, the client config, or `KC_HOSTNAME` can fix, because it has nothing
to do with Keycloak; it is the browser refusing to expose `crypto.subtle` to the page's own script
based on the page's origin alone.

**Result — in-cluster discovery leg: PASSES.** From a real Kubernetes `Pod` (`curlimages/curl`, not
the `kind` node container) inside the cluster:

