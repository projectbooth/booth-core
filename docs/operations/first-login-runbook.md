# First login (bundled Keycloak)

This is the sequence for a fresh install using the bundled identity provider default
(`keycloak.enabled`/`ingress.enabled`, both `true` by default — ADR 0106/0108). Every command
below was actually run against a real `kind` cluster while writing this, not transcribed from
memory — see the cross-references to the CI jobs that exercise the same sequence continuously.

## a) Install

The one value the chart cannot default for you is `ingress.host` — a hostname your devices and
router/DNS will resolve to this node (see item (f) below for what happens if it's wrong or
changes later). Everything else is optional:

```sh
helm install booth-core charts/booth-core \
  --namespace booth-system --create-namespace \
  --set ingress.host=booth.home.arpa \
  --set iframeSigningKey=$(openssl rand -hex 32) \
  --wait
```

- `ingress.host` is **required** whenever `ingress.enabled` and `keycloak.enabled` are both true
  (the bundled default) — the chart fails the install outright with a clear message if it's
  missing, rather than installing something that can't log anyone in.
- `iframeSigningKey` is **not** strictly required for a single-replica install (core falls back
  to an ephemeral key with a startup log line), but is recommended from the start — it becomes
  required once you ever run more than one replica (`internal/gateway/iframetoken.go`'s own doc
  comment explains why a shared key matters there), and there's no reason to leave it unset.
- Everything about Keycloak itself — the realm, the client, the database, the admin credential,
  the certificate — is provisioned automatically. Nothing else to pass.

If you're running an external identity provider instead of the bundled one, set
`keycloak.enabled=false` and the existing `oidc.issuerUrl`/`oidc.clientId` values — see
"Shared values across module installs" in `accounts-and-workspaces.md`.

## b) Retrieve the generated admin password and the CA

Both are generated by core itself at first boot, into Secrets — never a chart default
(ADR 0106 item 3 / ADR 0108 item 2(b)):

```sh
# Keycloak's bootstrap admin password (username is always "admin"):
kubectl -n booth-system get secret booth-keycloak-admin -o jsonpath='{.data.password}' | base64 -d; echo

# The self-signed CA, if you're using the chart-generated certificate (the default, mode (b) of
# three -- see ADR 0108 item 2). Skip this if you supplied your own certificate Secret or use
# cert-manager instead.
kubectl -n booth-system get secret booth-core-tls -o jsonpath='{.data.ca\.crt}' | base64 -d > booth-ca.crt
```

**Trusting the CA**, so your browser/OS stops warning about it:
- **Quick, per-device, no import**: just click through the browser's warning once per
  browser/device ("Advanced → Proceed", Chrome's wording; "Accept the Risk" in Firefox). This is
  the same experience as most self-hosted homelab appliances (Proxmox, TrueNAS, pfSense) that
  ship a self-signed certificate by default.
- **Import once, trusted everywhere after**: import `booth-ca.crt` into your OS or browser trust
  store (System Settings → Certificates on most platforms; `about:preferences` → Certificates in
  Firefox; the exact steps are OS/browser-specific and not reproduced here).

## c) First-login sequence with booth-admin

`scripts/booth-admin` never talks to Keycloak over a non-local `http://` URL (it refuses one
outright — see `accounts-and-workspaces.md`), so reach it through a port-forward, the same way
for every one of these commands:

```sh
kubectl -n booth-system port-forward svc/booth-core-keycloak 8081:8080 &

export KEYCLOAK_URL=http://localhost:8081
export KEYCLOAK_REALM=booth          # the chart's fixed starter-realm name
export KEYCLOAK_ADMIN_USER=admin     # the chart's fixed bootstrap admin username
export KEYCLOAK_ADMIN_PASSWORD=<from step (b)>

python3 scripts/booth-admin create-workspace home
python3 scripts/booth-admin create-user alice --email alice@example.com --name "Alice Smith"
python3 scripts/booth-admin add-member alice home owner
```

**Harden the master realm now**, not later — `--import-realm` only ever runs on Keycloak's first
boot and cannot touch the already-existing master realm, and the master realm ships with
brute-force protection *off* by default:

```sh
python3 scripts/booth-admin harden-master
```

Safe to re-run; it's a no-op once already enabled (and this is the exact sequence
`bundled-keycloak-check`'s CI job runs and re-verifies through the admin API on every push to
`master`).

**If you need to reset someone's password later** (there is no mail server, so this is the only
recovery path for a locked-out user):

```sh
python3 scripts/booth-admin set-password alice
```

Both `create-user` and `set-password` print a temporary password once, require a change at next
login, and never log or save it anywhere — hand it to the person through whatever channel you'd
use for any other credential handoff.

**Then sign in for real**: open `https://<ingress.host>/` in a browser (trusting the CA, or
clicking through the warning, per step (b)), sign in as `alice` with the temporary password
printed above, and Keycloak's own "update your password" screen takes over from there — this
part needs the shell (`booth-design`), which is a separate chart/repo from `booth-core` and not
covered by this install.

## d) Creating a permanent admin, and what happens to the bootstrap Secret

Keycloak 26's bootstrap admin is **temporary** by design (ADR 0106 condition 5): the first time
you sign in to the admin console with it, Keycloak requires you to create a real, permanent
admin user before doing anything else — this happens through Keycloak's own UI, not a
`booth-admin` subcommand:

```sh
kubectl -n booth-system port-forward svc/booth-core-keycloak 8081:8080 &
# open http://localhost:8081/admin/ , sign in with "admin" / the password from step (b),
# follow Keycloak's own prompt to create a permanent admin.
```

Once you've done that, the bootstrap credential in `booth-keycloak-admin` stops being usable for
anything beyond that one-time flow (Keycloak's own behavior, not something this chart or
`booth-admin` enforces). Core does not delete the Secret itself — it's harmless to leave in
place, or you may delete it once you've confirmed your new permanent admin works.

## f) If `ingress.host` changes after first boot

The starter realm is only imported on Keycloak's first boot (`--import-realm`). Changing
`ingress.host` later (a `helm upgrade --set ingress.host=...`) updates core's own computed
values immediately — `KC_HOSTNAME`, `oidc.issuerUrl`, and the TLS certificate's SAN all recompute
and the certificate re-issues on its own (`internal/tlsprov`) — but the **shipped client's own
`redirectUris`/`webOrigins`, baked in at that first import, do not**. A browser login after the
host changes will fail with `Invalid parameter: redirect_uri` until you fix the client by hand.

**Tested, not assumed**: this was reproduced on a real cluster (install with one host, `helm
upgrade` to a second) and confirmed fixed by a direct, partial update to the client (Keycloak's
client PUT endpoint merges the fields you send — it does not require the full representation the
way the realm PUT does; every other client setting, including the audience mapper, survives
untouched):

```sh
kubectl -n booth-system port-forward svc/booth-core-keycloak 8081:8080 &
ADMIN_TOKEN=$(curl -s -X POST http://localhost:8081/realms/master/protocol/openid-connect/token \
  -d "grant_type=password&client_id=admin-cli&username=admin&password=<admin password>" \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['access_token'])")
CLIENT_ID=$(curl -s "http://localhost:8081/admin/realms/booth/clients?clientId=booth-design" \
  -H "Authorization: Bearer $ADMIN_TOKEN" | python3 -c "import sys,json; print(json.load(sys.stdin)[0]['id'])")
curl -X PUT "http://localhost:8081/admin/realms/booth/clients/$CLIENT_ID" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"redirectUris":["https://<new-host>/*"],"webOrigins":["https://<new-host>"]}'
```

## g) Admin console exposure

The admin console (`/admin/*`) and the master realm (`/realms/master/*`) are **never** routed
through the Ingress — neither path is matched by either of its two rules, confirmed by
`ingress-tls-check`'s own CI assertions, which check this on every push, not just once. The only
way to reach them is the port-forward shown in (c)/(d) above.

The bundled Keycloak's `NetworkPolicy` admits ingress from **any namespace** on port 8080 — not
scoped to database-client-style labels the way the bundled PostgreSQL's policy is, because every
module's own pod needs to reach Keycloak's discovery/JWKS endpoints to verify tokens (ADR 0041),
which is the whole fleet, not an opt-in subset. Stated plainly rather than looking more
restrictive than it is: within the cluster, any pod can reach Keycloak's `:8080`, including its
own admin REST API, if it has (or can guess) valid credentials. The real security boundary is the
generated admin password itself, not network isolation.

## h) Backups (ADR 0109)

This homelab posture is a **warm standby**, not automatic failover (ADR 0109) — losing the node
means a manual restore, not seamless continuation.

- **Set `postgresql.backup.s3.bucket`** (or copy the scheduled dump off the node some other way).
  The default backup destination is a PVC on the *same* cluster, which is useless if you lose
  that node — see `docs/runbooks/postgres-backup-restore.md`.
- **The cluster's own Secrets are not in Postgres and are not covered by that backup at all.**
  Core's workload-token signing keys, the NATS operator/account keys, the bundled Postgres and
  Keycloak admin passwords, and every module's minted credentials live only as Kubernetes
  Secrets, in the cluster's own datastore (etcd on a single-server k3s install). A Postgres
  restore onto a fresh cluster without these loses them and mismatches database roles. Take
  scheduled snapshots of the cluster's own datastore to an off-node location too (`k3s
  etcd-snapshot`, pointed at S3 or a path) — this is separate from, and in addition to, the
  Postgres backup above.
- **Module data on node-bound volumes is separate again** (object-store contents, log storage,
  notebook home directories) — neither backup above covers it. Check each module's own runbook
  for what it stores outside Postgres.
- **A restore has not been drilled from this repo's own CI.** Until a real restore-onto-a-clean-
  node run has passed, treat "this will survive losing the node" as a goal, not a verified
  property (ADR 0109's own framing).

## i) LAN only — do not expose this publicly

There is no rate limiting anywhere in this platform yet, and **ADR 0101 explicitly forbids
exposing core to the public internet while any module declares `publicRoutes`** — a public route
skips authentication entirely by design (API keys, not a login), and without rate limiting that
is not a safe thing to put on the open internet. This bundled-install posture (a self-signed
certificate, a LAN hostname) is built for reachability from your own devices on your own network,
not for a public-facing deployment — that remains a decision ARCHITECTURE item 37a has not made.
